# Contributing to DBSnap

Welcome to the DBSnap team! We value clarity, precision, and efficiency.

## Philosophy
**Clarity > Complexity.**
We are building a tool for developers who want peace of mind. Our code should reflect that: clean, understandable, and safe.

## Workflow

1.  **Issue First**: Every piece of work must start with an issue (or a task in `TODO.md`).
2.  **Branching**: `feat/ISSUE-ID-description` or `fix/ISSUE-ID-description`.
3.  **One Issue = One PR**: Do not bundle unrelated changes. Small PRs are easier to review.

## Commit Conventions

We follow [Conventional Commits](https://www.conventionalcommits.org/):

-   `feat`: A new feature
-   `fix`: A bug fix
-   `docs`: Documentation only changes
-   `style`: Changes that do not affect the meaning of the code (white-space, formatting, etc)
-   `refactor`: A code change that neither fixes a bug nor adds a feature
-   `test`: Adding missing tests or correcting existing tests
-   `chore`: Changes to the build process or auxiliary tools and libraries such as documentation generation

**Example:** `feat(auth): implement jwt refresh token logic`

## AI Policy

-   **Verification**: If you use AI to generate code, YOU are responsible for verifying it.
-   **No Magic**: Do not commit code you do not understand.
-   **Transparency**: Mention if a PR was largely AI-generated so reviewers can pay extra attention to logical edge cases.
